# Inspection Workflow

## 1. 阶段边界

严格按准备、完整检查、报告、授权、修复、验证六个阶段执行。检查阶段不得修改业务代码或测试代码。

## 2. 准备

1. 解析用户请求和 Target Scope。
2. 识别技术栈、相关模块和测试命令。
3. 读取必要 Context Scope。
4. 检查 Git status、未提交修改和目标文件。
5. 建立本次场景检查清单。

## 3. 场景检查

每个适用场景均需：
- 读取对应场景文件。
- 检查其明确列出的风险模式。
- 记录证据位置和触发条件。
- 检查是否存在等效控制机制。
- 给出缺陷判定和检查执行状态。

不得把抽样检查描述为完整检查。若目标范围较大而无法全部检查，标记 Partial 并说明边界。

## 4. 问题归并

场景独立检查，之后统一按根因归并：

- 同一根因产生的多个现象合并成一个问题。
- 一个问题可以关联多个场景。
- 不同根因分别记录。
- 根因不清晰时保留独立问题或标记 Potential。
- 合并不得丢失证据、受影响位置和场景来源。

每个问题分配稳定的本次报告 ID，例如 FDG-001。

## 5. 完整报告

完成所有场景检查后统一输出检查报告。至少包含：
- Target Scope 与 Context Scope。
- 场景检查执行状态。
- 问题汇总与判定。
- 每个问题的证据、根因、影响和关联场景。
- 未检查内容、限制和阻塞。
- 是否建议修复及原因。

## 6. 修复执行

获得授权后：
1. 将授权与问题 ID 对应。
2. 重新检查目标文件，防止期间用户改动。
3. 为每个问题制定最小修改计划。
4. 修复独立问题；按依赖关系处理相互依赖的问题。
5. 运行对应测试和验证。
6. 检查 Diff 和业务语义。
7. 更新每个问题的修复状态。

独立问题修复失败不阻止其他独立问题。依赖问题失败时停止受影响的后续问题。

## 7. 部分成功

修复状态分别记录：
- Fixed：修复完成且验证达到预期。
- Fixed with limitations：修改已完成，但验证不完整。
- Not fixed：未修改或修复失败。
- Skipped：用户未授权或明确排除。
- Blocked：因冲突、环境或依赖无法继续。

不能因为部分问题成功就将整个任务报告为全部完成。
