# Safety and Business Logic Preservation

## 1. 证据标准

Confirmed 问题必须同时具备：

1. 明确的触发条件或执行路径。
2. 可从代码推导的当前行为。
3. 被违反的正确性约束。
4. 可说明的影响或错误结果。
5. 对等效控制机制的检查，确认没有其他逻辑已保证正确性。

不能仅因代码没有使用某种常见写法（例如没有 debounce、没有 AbortController、没有 mounted flag）就认定缺陷。

证据不足时标记 Potential，并明确缺失信息。

## 2. 业务语义不可变

除非该语义本身是已确认缺陷且用户明确授权，不得改变：

- 事件触发条件、操作时机和交互流程。
- API 调用条件、调用顺序、参数、调用时机和业务次数语义。
- 数据转换、筛选、排序、默认值和返回值。
- 业务状态、持久化时机和跨组件同步。
- 导航、埋点、缓存、通知及其他副作用。
- 业务校验、权限、错误提示和异常恢复策略。

添加防重复、取消请求或忽略过期响应时，必须先理解它是否会改变用户可观察到的业务行为。不能擅自把“重复调用”认定为错误；有些操作本身允许多次执行。

## 3. 最小修改计划

每个获准问题修复前，写出内部计划并在必要时向用户展示：

- 问题 ID 与根因。
- 允许修改的文件、函数和代码区域。
- 允许新增/调整的局部测试。
- 必须保持不变的业务行为。
- 验证方式。

业务代码修改范围必须在检查报告中有依据。新增测试只验证当前缺陷，不借机整理测试框架。

## 4. Diff 检查

修改后逐项确认：

- 所有变更都直接对应批准的问题。
- 没有超出允许文件或区域的业务代码改动。
- 没有无关重构、格式化、命名调整或依赖升级。
- API、数据、状态和副作用语义未被意外改变。
- 测试改动只覆盖当前缺陷。

出现越界时，停止继续修改并安全处理 Skill 自己的改动。

## 5. 工作区保护

修改前检查 Git status 和目标文件当前内容。不得覆盖、丢弃或重置用户未提交的工作。

若目标区域已有用户修改：
- 与修复无冲突且可安全叠加：保留原改动并进行最小补丁。
- 有冲突或无法判断归属：停止该问题，报告冲突。
- 不得使用 reset、clean、强制 checkout 或整文件覆盖来解决冲突。

只允许撤销能够明确识别为本次 Skill 自己产生的改动。不能安全区分时，不执行回滚。

## 6. 不确定性处理

不确定是否为缺陷、不确定修复是否保持业务语义，或无法证明修改范围局部时，只报告，不修改。不要为了完成任务而猜测。
