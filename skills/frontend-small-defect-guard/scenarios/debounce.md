# Scenario: debounce

## 检查目标

识别防抖或节流逻辑本身导致的可观察错误，包括计时器清理、闭包陈旧、参数丢失、调用时机错误和组件卸载后的延迟执行。

## 风险特征

- 每次输入都创建新 timer，但旧 timer 未清理。
- debounce 函数在 render/更新过程中反复创建，导致计时器无法合并。
- 延迟回调读取到过期 state/props。
- trailing/leading 行为与现有调用约定不一致。
- timer 未在卸载或依赖变化时清理。
- debounce 包装后丢失 this、参数、返回值或取消能力。
- throttle/debounce 混用，导致执行次数或时机不正确。

## 检查方法

1. 确认调用频率控制是否为当前业务明确要求，而不是自行建议添加。
2. 追踪 timer 创建、重置、执行和清理的完整生命周期。
3. 检查包装函数身份是否稳定，以及闭包读取的数据是否应为最新值。
4. 检查 leading/trailing、最大等待时间、取消和立即执行等实际配置。
5. 检查异步回调是否可能并发或产生过期结果；必要时关联 request-race。
6. 检查包装层是否保留原函数的参数和必要返回语义。

## 正确性约束

- debounce 应在约定等待窗口内合并调用，并在正确时机执行。
- throttle 应符合约定的最大执行频率。
- 新输入到来时，旧的待执行任务应按既定策略取消或替换。
- 生命周期结束后，不得遗留无效延迟副作用。
- 不能因防抖而丢失业务要求必须执行的最终输入或提交动作。

## 排除条件

- 用户尚未要求防抖/节流，且当前行为没有明确错误。
- 需要产品决定延迟时长、leading/trailing 或最大等待策略。
- 高频请求本身是业务要求，或服务端已有明确控制策略。

## 修复原则

- 优先修复 timer 生命周期和函数身份问题。
- 使用项目当前框架适配的稳定引用/清理方式，不强制特定 Hook 或工具库。
- 更新闭包数据时，先确认应该读取调用时快照还是执行时最新值。
- 不擅自改变等待时长、leading/trailing、调用次数或最终执行时机。
- 不把 debounce 当作请求竞态的替代方案。

## 验收标准

- 连续触发时符合既有 debounce/throttle 配置。
- 最终输入按约定执行，参数和上下文正确。
- 组件卸载或依赖变化后不存在残留 timer。
- 原有立即执行、取消和返回值语义未改变。

## 关联场景

- request-race：防抖不能保证已经发出的多个请求按顺序返回。
- component-lifecycle：timer 必须在适当生命周期清理。
- async-loading：延迟执行可能影响 Loading 状态起止时机。
