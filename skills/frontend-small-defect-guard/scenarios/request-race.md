# Scenario: request-race

## 检查目标

识别同一状态目标存在多个并发请求时，旧请求结果覆盖新请求结果、过期响应触发副作用或请求生命周期互相污染的问题。

## 风险特征

- 搜索词、筛选条件、路由参数变化后并发请求。
- 请求 A 后发但先返回，请求 B 先发但后返回，最终旧数据覆盖新数据。
- 组件切换实体后，旧实体请求更新当前视图。
- 旧请求的 finally 将新请求的 loading 清除。
- 旧请求错误覆盖新请求成功状态，或旧响应触发导航、提示、缓存写入等副作用。
- 仅取消请求但没有处理取消不生效或响应已完成的情况。

## 检查方法

1. 识别请求触发条件、状态写入位置和副作用位置。
2. 判断多个请求是否竞争同一个状态或业务实体。
3. 通过调用顺序与响应顺序构造竞态路径。
4. 检查是否已有 request key、sequence id、AbortController、数据层去重或框架查询缓存机制。
5. 检查成功、失败、finally 和取消路径是否都受当前请求身份约束。
6. 判断请求结果是否应按最新发起、最新完成或业务版本决定；不能自行选择策略。

## 正确性约束

- 只有当前有效请求可以更新其目标状态或触发相关副作用。
- 不同查询 key/实体的数据不能互相覆盖。
- 旧请求的 finally 不得结束新请求的 loading。
- 取消请求不等于保证响应绝不返回；仍需考虑过期响应保护。
- 对允许并发且结果均有意义的操作，不应施加全局 latest-wins 限制。

## 排除条件

- 服务端数据版本、事务顺序或一致性语义不明确。
- 多请求结果需要业务合并或冲突解决。
- 需要改造共享数据缓存、全局请求层或跨服务协议。
- 操作本身要求全部结果按业务顺序处理。

## 修复原则

- 仅在语义明确为“最新请求有效”时使用 request identity/sequence guard。
- AbortController 可用于减少无用工作，但不能在不验证语义时替代结果身份校验。
- 将状态写入和副作用都置于有效性判断之后。
- loading/error 等状态应与具体请求身份关联，避免旧请求清理新请求状态。
- 不擅自改变请求参数、触发条件、调用次数或 API 顺序。

## 验收标准

- 构造请求乱序返回时，最终状态符合既定有效性策略。
- 旧请求的成功、失败和 finally 均不能污染新请求状态。
- 切换实体或查询条件后，旧结果不显示在新目标上。
- 正常单请求和允许并发的业务流程保持不变。

## 关联场景

- async-loading：竞态经常表现为 loading/error 状态被旧请求覆盖。
- component-lifecycle：请求返回时组件可能已卸载或目标实例已替换。
- debounce：输入防抖不能消除已发出请求的竞态。
