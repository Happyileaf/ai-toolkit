# Frontend Small Defect Guard

## 1. 目标与定位

识别、报告并在获得授权后修复前端代码中的小型缺陷。关注的问题应同时具备以下特征：

- 高频：在常见前端交互或异步处理过程中反复出现。
- 低复杂度：触发条件和影响范围可以在局部代码中理解。
- 模式明确：存在成熟、可解释的正确性约束或修复方式。
- 局部影响：能够定位到有限的组件、函数或调用链。
- 可验证：可以通过静态检查、现有测试或局部测试验证修复。

本 Skill 不是通用 Bug 分析器、通用 Code Review、代码风格检查、重构工具或架构优化工具。

## 2. 核心原则

1. Small Problems Only：只处理符合本 Skill 定位的小型缺陷。
2. Scope First：严格遵守用户指定的 Target Scope。
3. Evidence-based Detection：必须以代码证据和可复现行为判断缺陷，不以缺少某种最佳实践写法作为缺陷证据。
4. Scenario Driven：按场景规则检查，不进行无边界扫描。
5. Root Cause Consolidation：按根因归并问题，一个问题可以关联多个场景。
6. Report Before Fix：必须先完成全部检查并统一报告，之后才能修改。
7. Business Logic Preservation：保护原有业务语义，优先级高于修复便利性。
8. Minimal Changes：仅修改修复缺陷所必需的最小范围。
9. Deterministic Verification：说明验证方式、实际结果和未验证部分。
10. Progressive Expansion：场景可逐步扩展，但不得降低现有安全标准。

## 3. 默认执行模式

默认使用 Report + Confirm：

1. 完成检查并输出完整报告。
2. 明确区分 Confirmed、Potential、Clean、Out of Scope。
3. 询问用户是否修复。
4. 用户确认后，只修复其授权的问题。
5. 未获得确认时不修改任何文件。

支持三种模式：

- Report Only：只检查和报告。
- Report + Confirm：默认模式，报告后等待用户确认。
- Report + Auto Fix：对满足自动修复准入条件的 Confirmed 问题自动修复；其余问题只报告。用户明确要求此模式时才启用。

用户可以选择全部问题、指定问题 ID、排除指定问题 ID，或暂不修改。不得将沉默视为授权。

## 4. 场景清单

第一版必须实现以下六个场景：

| Scenario | 目标 |
|---|---|
| duplicate-submit | 识别同一用户操作导致的非预期重复提交或重复副作用 |
| debounce | 识别防抖/节流实现中导致行为错误的缺陷 |
| request-race | 识别多个请求并发时过期结果覆盖新结果等竞态 |
| async-loading | 识别异步流程中 Loading、Error、Success 等状态不一致 |
| component-lifecycle | 识别组件卸载、重建或生命周期切换后仍执行无效副作用的问题 |
| input-boundary | 识别通用输入边界处理中的明确缺陷，不推断业务字段规则 |

每个场景的检查目标、证据要求、排除条件、修复原则和验收标准见 [scenarios/](./scenarios/)。

## 5. 执行流程

### Phase A：范围确认与准备

1. 识别用户指定的 Target Scope；若未指定，使用当前任务明确涉及的文件或模块，不默认扫描整个仓库。
2. 读取理解目标代码所必需的 Context Scope。读取上下文不代表扩大扫描或修改范围。
3. 检查工作区状态、未提交修改和项目测试/构建命令。
4. 识别项目技术栈和实际使用的框架、请求库、状态管理及测试工具，不强制统一实现方式。

### Phase B：完整检查

1. 匹配六个场景，必要时标记 Not Applicable。
2. 按场景规则检查目标范围。
3. 对每个候选问题收集证据：触发条件、当前行为、正确性约束、影响范围，以及等效控制机制是否已存在。
4. 判断问题状态：Confirmed、Potential、Clean 或 Out of Scope。
5. 检查全部目标场景后，按根因归并问题；保留场景关联。
6. 记录无法检查的文件、区域、测试或运行条件。
7. 完成所有检查后，统一输出检查报告。禁止边检查边修改。

### Phase C：授权与修复

1. Report + Confirm 模式下等待用户授权，并确认授权范围。
2. 对每个获准问题制定简短修复计划，列明业务代码范围、测试代码范围、允许修改和禁止改变的行为。
3. 修复前再次检查相关文件，确保没有覆盖用户新产生的修改。
4. 先修复根因明确、相互独立的问题；依赖问题按依赖顺序处理。
5. 可新增或调整针对当前缺陷的局部测试；不得借此重构测试架构或扩大业务代码修改范围。
6. 每个问题修改后执行适当验证，并检查 Diff 是否越界。
7. 汇总修复执行报告。修复阶段发现的新问题应记录并回到报告，不得未经授权顺手修复。

## 6. 缺陷判定与检查状态

缺陷判定结果与检查执行状态必须分开记录。

### 判定结果

- Confirmed：证据足以证明存在缺陷。
- Potential：存在风险迹象，但缺少足够证据确认。
- Clean：已完成相关检查，未发现该类缺陷。
- Out of Scope：问题不属于本 Skill 职责。

### 检查执行状态

- Completed：检查已完整完成。
- Partial：只完成部分检查。
- Blocked：因依赖、权限、环境或信息缺失无法检查。
- Not Applicable：该场景与目标代码无关。

Partial 或 Blocked 不得标记为 Clean。不能因为未发现问题就将未检查区域报告为通过。

## 7. 自动修复准入

只有同时满足以下条件的问题才允许自动修复：

- 判定为 Confirmed。
- 触发条件和根因明确。
- 修复方式成熟且确定。
- 修改范围局部、清晰。
- 不需要猜测产品或业务意图。
- 不改变业务逻辑、接口语义或副作用语义。
- 有可执行的验证方式。
- 不覆盖用户未提交的修改。

任一条件不满足，只报告，不自动修改。

## 8. 业务逻辑保护与修改边界

业务逻辑保护是最高优先级约束。不得改变：

- 用户操作触发业务动作的条件和时机。
- API 调用的条件、次数语义、顺序、参数构造及调用时机，除非该调用本身就是已确认缺陷且用户明确授权。
- 数据转换、默认值、排序、过滤、计算和返回值语义。
- 状态更新的业务含义、持久化时机和跨组件同步行为。
- 导航、埋点、通知、缓存、存储及其他副作用的语义。
- 业务规则、权限判断、校验规则和错误处理策略。

业务代码只能修改报告中明确涉及的最小位置。测试代码可以为当前缺陷新增或调整局部测试，但不得改变测试架构或以测试需要为由扩大业务代码修改。

如果修复必须改变上述行为，停止修改并向用户说明。

## 9. 工作区保护

- 修改前检查 Git 状态和相关文件内容。
- 保留所有用户已有的未提交修改。
- 不执行会丢弃或覆盖用户修改的操作，例如 reset、clean、强制 checkout 或无差别回滚。
- 如果用户修改与修复范围冲突，停止受影响问题并说明。
- 修复失败时只撤销 Skill 自己产生且能明确识别的改动；无法安全区分时不回滚，交由用户处理。
- 不擅自提交、推送、合并或改变分支。

## 10. 验证与完成标准

按缺陷性质和项目能力选择验证等级：

1. Static Inspection：检查代码路径、依赖关系、状态转换和 Diff。
2. Existing Tests：运行相关现有测试。
3. Targeted Tests：新增或运行针对当前缺陷的局部测试。
4. Runtime Verification：在可用环境中验证实际交互或运行行为。

每项验证记录 Passed、Failed、Partial 或 Not Verified。不得声称执行了未实际运行的测试。

修复后至少检查：
- 缺陷触发路径已被覆盖。
- 原有业务行为未被意外改变。
- 修改范围符合批准计划。
- 无无关代码、格式化或重构改动。
- 测试和静态检查结果已如实记录。

## 11. 报告

检查报告与修复执行报告分开：

- 检查报告：范围、场景覆盖、问题汇总、证据、根因、影响、检查限制和结论。
- 修复执行报告：授权问题、修改文件/位置、修改说明、测试、验证结果、未完成项和 Diff 范围检查。

模板见 [references/report-template.md](./references/report-template.md)。

## 12. 场景交叉与问题归并

独立场景分别执行检查，最终问题按根因归并：

- 同一根因导致多个表现时，合并为一个问题并关联多个场景。
- 不同根因即使发生在同一代码位置，也分别记录。
- 根因关系不确定时，不强行合并。
- 归并后保留各自证据和受影响位置，避免丢失细节。

## 13. 技术栈适应性

支持 React、Vue、Angular、原生 JavaScript/TypeScript 等常见前端技术栈。以行为约束和正确性为核心，不强制某种 Hook、Composable、状态管理或请求库。框架专属 API 仅在项目实际使用时采用。

## 14. 明确排除

以下情况不在本 Skill 范围内：

- 复杂业务规则、跨服务事务或跨系统一致性问题。
- 需要产品决策或业务意图推断的问题。
- 复杂状态机、复杂并发协议或大范围数据一致性问题。
- 性能专项优化、架构重构、代码风格和一般可维护性建议。
- 需要大范围重写或无法局部验证的问题。
- 仅凭“最佳实践”判断、没有实际错误证据的问题。

遇到排除项时简要说明原因；不要将其扩展成通用 Bug 调查。
