# 场景：component-lifecycle（组件生命周期）

## 检查目标

识别组件卸载、销毁、切换、重建或依赖变化后，异步任务、timer、订阅、事件监听器等仍执行无效副作用或资源未清理的问题。

## 风险特征

- timer、interval、DOM listener、observer、subscription 未清理。
- Promise 完成后更新已卸载组件或已切换目标的状态。
- effect/watch 依赖变化时旧任务没有清理。
- 事件监听器重复注册，导致一次事件触发多次回调。
- 组件实例重建后旧实例任务仍修改共享状态。
- cleanup 使用了已变化的引用或错误的资源标识。

## 检查方法

1. 识别组件或视图的创建、更新、卸载和重建路径。
2. 列出其创建的 timer、listener、observer、subscription、请求和异步回调。
3. 确认资源注册与释放成对出现，且 cleanup 使用同一资源标识。
4. 检查依赖变化时旧任务是否停止或失效。
5. 检查异步回调是否可能在卸载后、目标切换后执行副作用。
6. 区分框架允许的状态更新行为和真正的资源泄漏或错误副作用，不以旧式警告作为唯一证据。

## 正确性约束

- 组件不再拥有某项资源时，应按其生命周期释放资源。
- 过期实例或失效任务不得更新当前视图或触发不应发生的副作用。
- cleanup 不得误清理新实例创建的资源。
- 订阅和监听器不应重复注册或遗留。
- 请求取消或组件卸载不能改变本应持续完成的业务操作语义。

## 排除条件

- 任务有意跨组件生命周期持续执行，例如全局上传、后台保存或共享缓存更新。
- 资源由上层 Provider/Service 所有，目标组件并不拥有其生命周期。
- 需要重构全局资源管理或复杂导航缓存策略。
- 业务要求组件卸载后仍完成操作，但其所有权不明确。

## 修复原则

- 按资源所有权在正确生命周期注册和清理。
- 使用框架原生生命周期机制，不强制统一 Hook/Composable。
- 异步任务可以通过取消、有效性标记或请求身份保护，但选择必须符合业务语义。
- 不要仅为消除警告而取消本应继续的业务操作。
- 清理逻辑必须避免旧实例 cleanup 影响新实例资源。

## 验收标准

- 组件卸载或依赖变化后，不再发生属于旧实例的无效 UI 更新或副作用。
- timer、listener、observer、subscription 无重复注册或泄漏。
- 组件重新挂载后新实例功能正常。
- 需要跨生命周期继续的业务任务仍按原设计完成。

## 关联场景

- request-race：旧组件请求可能晚于新组件请求返回。
- debounce：延迟回调和 timer 需要生命周期清理。
- async-loading：组件失效后异步状态不应污染当前视图。
