# 场景：async-loading（异步状态一致性）

## 检查目标

识别异步流程中的 Loading、Success、Error、Empty 等状态未按真实请求生命周期更新，导致界面状态残留、提前结束或互相覆盖的问题。

## 风险特征

- loading 在请求开始前未设置，或请求结束后未恢复。
- 只在成功分支清理 loading，异常路径遗漏。
- 多个并发操作共享一个布尔 loading，某个请求结束就错误清除其他请求的状态。
- 请求失败后旧数据、错误提示和成功状态组合不一致。
- loading 状态更新与请求身份不匹配。
- 组件卸载后更新状态，或状态被旧异步任务覆盖。

## 检查方法

1. 梳理异步状态及其转换路径：idle → loading → success/error。
2. 检查同步异常、Promise rejection、成功、失败和取消路径。
3. 检查 finally 是否总能执行，以及其状态清理是否属于当前请求。
4. 判断 loading 是单请求状态、并发计数、按 key 状态还是页面级状态。
5. 检查空数据、旧数据保留、错误提示是否有明确既有语义。
6. 关联 request-race 与 component-lifecycle 检查异步任务有效性。

## 正确性约束

- Loading 必须反映对应操作是否仍在进行。
- 成功、失败和取消路径都必须遵守既有状态转换。
- 并发操作不得互相错误清理状态。
- Error、Empty、Success 的优先级和数据保留策略必须来自现有业务行为，不可推断。
- 不得因修复状态显示而改变请求行为或业务结果。

## 排除条件

- 产品尚未定义 loading/error/empty 的展示策略。
- 多个业务操作的状态关系复杂，需要重新设计状态机。
- 需要改变全局状态管理或跨页面数据一致性。

## 修复原则

- 优先补齐明确遗漏的状态转换和异常清理。
- finally 适合表达无论成功失败都要执行的清理，但需确保不会清理其他请求的状态。
- 并发场景应按请求身份或既有并发模型管理，不可简单增加一个布尔值。
- 不擅自增加骨架屏、Toast、自动重试、数据清空或成功提示。
- 若状态设计本身无法在局部安全修复，只报告。

## 验收标准

- 成功、失败和取消路径均进入正确终态。
- 请求进行期间 loading 不会提前消失，结束后不会永久残留。
- 并发请求之间状态互不污染。
- 原有数据保留、错误提示和空状态行为不变。

## 关联场景

- request-race：旧请求可能覆盖新请求的状态。
- duplicate-submit：pending 状态可能用于阻止重复提交。
- component-lifecycle：卸载后异步状态更新需受到生命周期约束。
