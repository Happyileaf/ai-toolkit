# 场景：duplicate-submit（重复提交）

## 检查目标

识别同一用户意图在短时间内触发多次，且业务上不应重复执行的提交或副作用。重点关注按钮、表单、键盘快捷键、事件冒泡，以及多个入口共用同一动作的情况。

## 风险特征

- 同一个提交处理器可能被 click、submit、Enter 等多个入口触发。
- 异步操作尚未结束时，入口仍可再次触发。
- UI 禁用状态更新晚于事件触发，无法阻止同一 tick 内的重复调用。
- 同一业务动作被多个事件监听器或父子组件重复调用。
- 防重复标记未在成功、失败或异常路径正确释放。

## 检查方法

1. 沿用户交互入口追踪到最终业务动作或 API 调用。
2. 确认业务是否要求单次操作互斥；不要假设所有重复调用都是错误。
3. 检查是否已有同步锁、进行中状态、表单提交状态、请求层去重或服务端幂等保障。
4. 检查多入口是否汇聚到同一个 handler，以及事件是否可能冒泡或重复绑定。
5. 检查锁的设置时机是否早于第一个 await，释放路径是否覆盖成功、失败和同步异常。
6. 检查锁作用域是否正确：组件实例、业务实体或全局范围不能混淆。

## 正确性约束

- 同一不可并发的用户操作在前一次完成前不得重复启动。
- 互斥状态必须在异步操作真正开始前同步建立。
- 成功、失败、异常和取消路径必须按原有业务流程正确结束互斥状态。
- 不得阻止业务明确允许的多次操作、不同实体操作或用户主动重试。

## 排除条件

- 服务端是否幂等、是否允许重复创建等业务语义不明确。
- 重复调用属于业务允许行为。
- 需要修改 API 协议、后端幂等策略或跨页面锁机制。
- 需要重新设计表单交互或提交流程。

## 修复原则

- 优先复用现有 pending/loading 状态或已有锁机制。
- 若 UI 状态更新存在时序窗口，只有业务语义明确时才考虑同步 ref/变量作为互斥门闩。
- 仅在提交入口增加最小保护，不改变参数、调用顺序、成功处理、错误提示和重试语义。
- 使用 finally 释放锁前，确认不会与后续请求或不同操作的状态竞争。
- 不要只通过按钮 disabled 解决所有重复入口问题；检查真正的动作边界。

## 验收标准

- 连续快速触发同一操作时，只启动一次不允许并发的业务动作。
- 通过 Enter、点击或其他已有入口触发时行为一致。
- 请求成功和失败后，原有可再次提交行为保持不变。
- 不同业务实体或明确允许并发的操作不被错误拦截。

## 关联场景

- async-loading：pending 状态可能同时承担 UI 状态与互斥门闩职责。
- debounce：输入触发的请求频率控制可能与重复提交表现重叠。
