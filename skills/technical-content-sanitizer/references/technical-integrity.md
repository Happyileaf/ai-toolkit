# 技术事实保护（Technical Integrity）

## 1. 基本原则

允许改变敏感信息的表达方式，不允许擅自改变技术事实。脱敏和公开化重构必须保持原始资料能够支持的事实、因果关系、技术机制和结论边界。

## 2. 内容区分

| 内容类型 | 处理原则 |
|---|---|
| 技术原理 | 尽可能保留；不得改变机制解释 |
| 技术实现 | 保持准确；内部名称可替换，但职责和关系不变 |
| 实际参数和版本 | 判断是否敏感；不得擅自改成另一个“真实值” |
| 企业与业务背景 | 可以删除、泛化或重写 |
| 示例或演示数据 | 可合成，但必须标记为示例/模拟 |
| 分析推断 | 明确标注为推断，不得改写成已证实事实 |

## 3. 不允许的变化

- 改变故障原因、触发条件、因果顺序或根因。
- 将相关性改写为因果关系。
- 擅自补充版本号、配置值、部署环境、指标、时间或实验结果。
- 把推测、假设或未验证的解释写成确定结论。
- 为了文章完整而编造测试、验证或修复效果。
- 修改参数后仍声称它是原始生产参数。
- 将单个案例扩大成普遍规律。
- 将企业专属实现重写成原文并未支持的通用技术结论。

## 4. 参数和数据处理

若真实参数或业务数据不宜公开，优先删除或用区间、量级表达；如需合成，明确标记“示例值”“模拟数据”。不得使用合成值推导原始案例没有支持的性能或故障结论。如果参数是理解问题的关键且无法安全替换，向用户说明冲突并请求确认。

## 5. 技术事实追踪

处理前提取关键事实，包括组件职责、调用关系和执行顺序、问题表现和触发条件、影响范围、根因及证据、解决方案和验证结果、事实/推断/未知项边界。重构后逐项对照。发现事实缺失、关系变化或无证据新增时，先修正；无法修正时标记 Needs Revision 或 Incomplete。

## 6. 公开文章的重构

模式 B 可以调整标题、结构、叙述顺序和表达方式，例如将内部事故记录整理为背景、现象、排查过程、根因分析、解决方案、验证和经验总结。但不能为了叙事流畅而虚构背景、对话、时间线、监控数据、实验或结果。对于原文没有提供的信息，使用明确的限制说明或省略。
