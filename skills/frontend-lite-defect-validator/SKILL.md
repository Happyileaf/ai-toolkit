# Frontend Lite Defect Validator

## 1. 技能目标

接收已有的前端潜在缺陷问题清单，通过阅读相关代码、追踪必要调用关系、理解业务约束和检查现有保护机制，对清单中的每个问题进行独立核实。

本技能的目标是判断每个输入问题是否真实成立，并提供有代码证据支持的确认结果，降低人工筛查误报的成本。

本技能是核实工具，不是问题发现器、修复器或缺陷管理工作流。

## 2. 核心原则

1. **Independent Validation**：原始报告是待验证的主张，不是事实；必须独立检查代码。
2. **Evidence-based Judgment**：所有结论必须由具体代码事实、执行路径或必要测试支持。
3. **Business Logic Preservation**：尊重项目实际业务约束，不把最佳实践偏好当作 Bug。
4. **Conservative Filtering**：只有存在充分反证时才判定 False Positive；证据不足时保留 Unverified。
5. **One-to-One Correspondence**：每个输入问题必须且只能对应一个输出核实结果。
6. **Analysis Reuse, Result Separation**：相同根因可以复用分析，但绝不能合并问题条目或核实结果。
7. **Read-only Validation**：只读取和分析，不修改业务代码、配置或原始问题清单。
8. **Minimal Necessary Inspection**：围绕输入问题检查必要代码，不重新扫描整个项目。
9. **Honest Verification**：如实记录未能访问的代码、无法执行的测试和判断限制。

## 3. 输入要求

### 3.1 支持的输入来源

支持任意来源的问题清单，包括：
- 其他 Skill 输出的问题报告，例如 Frontend Lite Defect Guard。
- ESLint 或其他静态分析工具输出。
- Markdown、JSON 或其他可读格式的问题文档。
- 用户直接提供的问题描述、问题列表或代码位置。

不得要求问题清单必须采用某个固定格式，也不得依赖特定上游 Skill 的内部结构。

### 3.2 提取问题信息

对每个问题尽可能提取：
- 原始编号或标识（Original ID）。
- 标题和问题描述。
- 文件路径及代码位置。
- 问题类型或分类。
- 报告声称的触发条件。
- 预期行为。
- 原始报告提供的证据和分析理由。
- 原始报告提供的修复建议（仅作为待验证信息）。

缺失信息可以通过必要的代码检查补充。不得编造原始输入未提供的信息；无法补齐且影响判断时，标记 Unverified 并说明原因。

### 3.3 原始输入只读

保留原始问题描述、标识和输入顺序。不得修改、重写、删除或覆盖原始问题清单。

## 4. 核实状态与置信度

每个问题必须且只能有一个 Verdict：
- **Confirmed**：有充分证据证明缺陷真实存在。
- **Likely**：有较强证据表明缺陷存在，但缺少关键验证或上下文。
- **Unverified**：当前证据或环境不足，无法可靠判断。
- **False Positive**：有充分反证证明原始报告描述的问题不成立。

每个问题还必须有一个独立的 Confidence：
- **High**：证据充分，判断可靠。
- **Medium**：主要依据已具备，但仍有一定不确定性。
- **Low**：判断依据有限，可靠程度较低。

Verdict 与 Confidence 不可混用。Severity 不是核实状态，也不能影响 Verdict 判定。

## 5. 执行流程

### 阶段 A：解析与登记

1. 读取完整问题清单。
2. 统计输入问题总数。
3. 为每个问题建立独立记录，保存原始 ID、描述、定位和输入顺序。
4. 建立输入问题与输出记录的一一对应关系。
5. 不因格式差异、描述相似或重复问题而减少记录数量。

### 阶段 B：整理关联关系

识别完全重复的问题、相同根因的问题，以及描述相似但实际场景不同的问题。

此步骤仅用于提高分析效率：
- 可以建立关联关系和复用证据。
- 不得合并问题记录。
- 不得提前判定不同问题具有相同结论。
- 不得减少最终输出条目。

### 阶段 C：逐项核实

针对每个问题，围绕其主张检查必要代码，并按需追踪调用方、被调用方、状态变化、业务约束和现有保护机制。具体标准见 [核实维度](./rules/validation-dimensions.md)。

### 阶段 D：必要的局部测试

当静态代码分析不足以判断、且测试成本合理时，可以运行相关现有测试或必要的局部测试。测试不是必经步骤。不得默认运行完整测试套件，不得为测试修改业务代码。

### 阶段 E：独立形成结论

为每个输入问题分别确定 Verdict、Confidence、核实依据和判断理由。即使多个问题共享根因，也必须确认各自代码位置、触发条件和业务场景，并分别输出结论。

### 阶段 F：生成与校验报告

按 [报告模板](./references/report-template.md) 输出：
1. 问题确认列表。
2. 问题确认详情。

报告必须保留输入顺序，严格一一对应。完成后执行 [一一对应与完整性检查](./rules/one-to-one-correspondence.md)。未通过完整性检查不得交付报告。

## 6. 输出要求

报告固定分为两个主要部分：

- **问题确认列表（Validation Summary）**：每个输入问题一行，快速呈现原始标识、问题描述、Verdict、Confidence、简要结论和关联问题。
- **问题确认详情（Validation Details）**：按照输入顺序逐个描述每个问题的原始主张、核实过程、证据、判断理由和关联问题。

报告可以提供各 Verdict 数量统计，但统计不能替代逐项结果。输入 N 个问题，必须输出 N 条列表记录和 N 份对应详情。

Unverified 单独标识或分组展示时，也必须保留在原始顺序对应的完整报告中；不得从列表或详情中省略。

## 7. 执行边界

- 阅读相关代码、类型、配置和测试：允许。
- 追踪必要调用关系：允许。
- 执行必要的局部测试：允许。
- 默认执行完整测试套件：不允许。
- 修改业务代码、测试代码或配置：禁止。
- 修改原始问题清单：禁止。
- 自动修复或生成修复补丁：禁止。
- 生成修复计划、下游任务或工作流：不负责。
- 指导下游如何消费核实报告：不负责。

本技能只交付输入问题清单的核实报告。报告之外不主动引导后续处理流程。
