# 核实工作流

## 1. 阶段一：解析输入

1. 读取完整的问题清单。
2. 确定问题条目边界和输入顺序。
3. 统计问题总数。
4. 为每个条目建立独立记录。
5. 保存原始 ID、标题、描述、定位和原始证据。
6. 检查输入是否有歧义；若歧义会影响条目数量或对应关系，先向用户询问必要信息。

不得因为格式不统一而自行丢弃条目。

## 2. 阶段二：整理关联

识别重复描述、相同根因和相似场景。建立关联关系，供后续复用分析。

整理阶段不得决定合并输出，也不得跳过任何问题。

## 3. 阶段三：逐项核实

对每个问题：
1. 从原始代码位置开始阅读。
2. 确认报告描述的代码行为。
3. 追踪必要的调用关系和状态变化。
4. 检查触发条件和实际可达路径。
5. 理解业务约束和预期行为。
6. 检查已有保护机制是否覆盖当前路径。
7. 判断实际影响。
8. 按证据确定 Verdict 和 Confidence。
9. 记录文件位置、证据和判断理由。

可复用已阅读的代码和分析结果，但仍须逐项确认当前问题的定位、触发条件、保护机制和影响。

## 4. 阶段四：必要的局部测试

仅当静态分析无法明确判断，且测试成本合理时执行。优先使用现有测试；必要时执行最小范围的局部测试。测试不是必经步骤，不默认运行完整测试套件，不修改任何项目文件。

记录测试是否执行、实际命令、覆盖范围和结果。不能将未执行的测试描述为通过。

## 5. 阶段五：独立形成结论

每个问题单独记录：
- 原始 ID 和报告编号。
- 原始问题描述。
- Verdict。
- Confidence。
- 核实过程。
- 证据。
- 判断理由。
- 关联问题（如有）。
- 未确认事项或限制（如有）。

每个问题必须有自己的判断。不能只写“同上”或只引用其他问题结论而不说明当前问题为何得到该结论。

## 6. 阶段六：生成报告

按照报告模板先输出问题确认列表，再按原始顺序输出全部问题确认详情。

列表和详情必须逐条对应。Unverified 问题也必须出现在两部分中。

## 7. 阶段七：完整性校验

按照 one-to-one-correspondence 规则检查输入数量、输出数量、原始 ID、输入顺序、Verdict 数量统计和列表详情对应关系。发现遗漏或重复时修正后再交付。

## 8. 部分完成

若问题数量过多、上下文缺失或环境限制导致无法完成全部深入核实：
- 不得静默省略问题。
- 已完成的问题按证据给出结论。
- 未能完成的问题逐项标记 Unverified，并说明具体限制。
- 仍需输出与输入一一对应的完整列表和详情。
