# 核实原则

## 1. Independent Validation

原始问题报告只是待验证的主张，不是已经确认的事实。不得直接采信原始报告的结论、风险等级或修复建议。

必须重新阅读实际代码和必要上下文，独立判断：
- 原始报告描述的代码行为是否存在。
- 报告所述触发条件是否成立。
- 是否存在实际错误或业务影响。
- 是否有报告未考虑的保护机制或业务约束。

## 2. Evidence-based Judgment

所有 Verdict 都必须由可定位、可解释的证据支持。证据可以来自实际代码、调用关系、状态转换、业务约束、已有测试或必要的局部测试。

不能仅凭：
- 缺少某种常见最佳实践写法。
- 静态分析工具发出警告。
- 代码风格或个人偏好。
- 变量、函数或文件命名。
- 原始报告给出的推测。
判定问题成立。

## 3. Business Logic Preservation

必须理解现有业务语义。常见实践不是普遍适用的业务规则。

例如：
- 某操作允许重复执行，不一定是重复提交缺陷。
- 请求没有取消机制，不一定存在生命周期缺陷。
- 请求并发不一定意味着旧响应必须被丢弃。
- 状态没有立即更新，不一定代表异步状态错误。
- 输入没有额外校验，不一定违反业务约束。

只有能够说明当前行为违反了什么实际预期，并造成或可能造成什么错误，才可确认缺陷。

## 4. Conservative Filtering

过滤误报必须有积极反证。未找到问题、未能复现或代码上下文不完整，不等于 False Positive。

- 证据充分：Confirmed。
- 有较强迹象但缺少关键验证：Likely。
- 证据不足：Unverified。
- 有充分反证：False Positive。

不得为了降低人工确认量而把不确定问题强行过滤。

## 5. Root Cause Awareness

识别多个问题之间的相同根因，帮助复用代码阅读和分析结果。但不同输入问题始终保留独立身份和独立结论。

相同根因不意味着：
- 代码位置相同。
- 触发条件相同。
- 保护机制覆盖范围相同。
- 实际影响相同。
- Verdict 必须相同。

必须逐个确认这些差异。

## 6. Minimal Necessary Inspection

检查范围围绕输入问题展开。优先从报告所指代码位置开始，按需阅读直接调用方、被调用方、相关状态管理、共享封装和测试。

不因执行本技能而重新扫描整个项目或主动寻找无关问题。

## 7. Honest Verification

明确区分代码事实、分析推断和未知信息。不得声称运行了未执行的测试，不得将无法访问或未检查的代码描述为已验证。无法确认时说明具体阻碍并使用 Unverified。
