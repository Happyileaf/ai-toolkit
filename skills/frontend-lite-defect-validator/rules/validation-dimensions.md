# 核实维度

每个输入问题均应根据其主张核实以下维度。无需机械地对每个问题执行相同深度的分析；一旦证据已经足以得出可靠结论，可以停止无关检查。

## 1. Existence：问题真实性

确认原始报告描述的代码行为是否真实存在。

检查：
- 报告指向的代码和逻辑是否存在。
- 函数、事件、请求或状态更新是否按报告所述执行。
- 原始报告是否误解了执行顺序、数据流或代码职责。
- 文件位置、调用关系或前提条件是否准确。

如果报告所描述的代码行为本身不存在，并且有代码证据支持，可以判定 False Positive。

## 2. Triggerability：问题可触发性

确认实际运行中是否存在合理的触发路径。

检查：
- 报告声称的前置条件是否可能成立。
- 用户或系统能否进入相关执行路径。
- 是否存在状态、权限、路由或生命周期约束。
- 是否有其他逻辑提前阻止问题发生。
- 风险是否只是理论可能，而没有实际可达路径。

不能只凭某段代码看起来存在风险，就推断用户一定能够触发它。

## 3. Impact：实际影响

确认可触发的行为是否构成真实缺陷。

检查：
- 是否产生错误结果或错误状态。
- 是否破坏既定业务流程。
- 是否影响其他组件、页面或业务实体。
- 是否产生用户可感知的异常或错误副作用。
- 是否违反可以从代码、需求或业务约束中确认的预期。

如果行为存在但符合业务预期，或不会造成报告声称的错误，不能仅凭代码形式认定为缺陷。

## 4. Existing Safeguards：现有保护机制

检查原始报告是否遗漏其他代码路径或机制，例如：
- 上层组件限制重复操作。
- 请求层处理请求身份或竞态。
- 状态更新具有条件约束。
- 统一封装负责资源清理。
- 框架或数据层提供等效保护。
- 业务流程保证相关状态一致。

必须确认保护机制覆盖当前问题的具体执行路径、状态和副作用。仅仅存在一个公共封装或保护函数，不代表它一定覆盖当前场景。

## 5. 维度之间的关系

通常按以下顺序分析：
1. 真实性：报告描述的行为是否存在？
2. 可触发性：是否有实际可达的触发路径？
3. 实际影响：是否违反预期并造成错误？
4. 现有保护机制：是否已有逻辑使问题无法发生或不再产生所述影响？

这不是僵硬的流水线。如果前一步已有充分反证，可以提前结束；如果业务语义未知，应保留不确定性。
