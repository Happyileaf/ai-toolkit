# 证据要求

## 1. 通用要求

每个核实结果都必须有与该问题直接相关的证据和判断理由。优先提供仓库内可定位的文件路径、行号、函数或组件名称。

证据描述应区分：
- **代码事实**：代码实际做了什么。
- **执行推断**：根据调用关系、状态和条件推导出的行为。
- **业务约束**：从项目代码、类型、配置、测试或用户提供的资料中确认的预期。
- **测试结果**：实际执行的测试、命令和结果。

不得把推断写成已经观察到的运行事实。

## 2. 各 Verdict 的证据门槛

### Confirmed

至少能说明：
1. 具体代码位置或执行路径。
2. 触发条件如何成立。
3. 当前行为如何违反正确性约束或业务预期。
4. 实际影响或可由代码明确推导的影响。
5. 已检查与问题相关的等效保护机制。

### Likely

必须指出具体风险代码和合理触发路径，并明确尚缺少的关键证据。不得仅凭抽象风险或编码风格判断。

### Unverified

说明当前已检查的内容、缺失的信息、受阻原因，以及这些信息为什么决定是否成立。

### False Positive

指出原始报告忽略的具体事实或反证，并说明该事实如何否定原始问题主张。不能只写“未发现问题”或“无法复现”。

## 3. 测试证据

测试只在有必要且成本合理时执行：
- 优先运行已有相关测试。
- 必要时运行局部测试或最小复现。
- 不默认执行完整测试套件。
- 不为测试修改业务代码或配置。
- 记录实际命令、覆盖的行为和结果。

测试状态使用：
- **Passed**：实际执行且通过。
- **Failed**：实际执行且失败。
- **Partial**：只覆盖部分条件。
- **Not Run**：未执行，并说明原因（如适用）。

测试未执行不妨碍基于充分静态证据得出结论；但不能虚构测试结果。

## 4. 证据不足时的处理

- 不猜测隐藏的业务约束。
- 不假定未读取的公共封装一定提供保护。
- 不假定测试覆盖了未检查的分支。
- 不把工具警告当作缺陷证据。
- 不将“没有看到反证”当作问题成立的充分证据。
- 不将“没有看到问题”当作 False Positive 的充分证据。

必要时使用 Unverified，并清楚说明不确定性来源。
