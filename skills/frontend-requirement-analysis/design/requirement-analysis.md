# 需求分析规范

## 1. 文档目的

本文定义 `frontend-requirement-analysis` 对输入资料进行分析、筛选、关联和前端视角重构时所遵循的规范，包括资料管理、分块策略、前端相关性、信息确定性、需求范围、需求信息模型和最终文档组织。

本规范与 [Skill 设计说明](./skill-design.md) 配套；质量检查与三层追溯的验收要求见 [质量保障规范](./quality-assurance.md)。

## 2. 分析对象与资料管理

### 2.1 输入类型

不限定资料格式。可分析：

- 主 PRD、补充 PRD、修订说明。
- Axure/Figma 原型、截图、流程图、状态图和架构图。
- API/接口文档、数据字典。
- 需求评审记录、会议纪要和补充说明。
- 用户指定的其他资料。

V1 不强制读取代码仓库。用户明确要求时，代码信息可以作为辅助证据，但应标明其来源类型，不能将实现现状自动等同于产品要求。

### 2.2 Source Index

开始分析时建立资料清单。每项资料至少记录：

| 字段 | 含义 |
|---|---|
| `source_id` | 稳定来源标识，如 SRC-001 |
| `name` | 文件或资料名称 |
| `type` | PRD、prototype、diagram、API、meeting-note 等 |
| `version` | 资料明确标示的版本；无法确认则留空或标记 unknown |
| `modules` | 涉及的业务模块 |
| `summary` | 资料主要内容 |
| `relations` | 与其他资料的补充、修订、引用或冲突关系 |
| `readability` | 可读取、部分可读取、不可读取 |
| `notes` | 其他限制或判断依据 |

不得仅凭文件修改时间认定资料优先级。若不同资料的版本关系、权威性或适用范围不明确，应记录不确定性，不擅自选择一份作为唯一正确版本。

### 2.3 资料结构与分析单元

先识别每份资料的目录、章节、页面、图像或其他可定位单元，再按结构和业务边界开展分析。

分析单元优先采用：
- PRD 的章节或子章节。
- 原型中的页面、弹窗、状态或交互场景。
- 流程图中的节点、分支或子流程。
- 接口文档中的接口、字段或错误定义。
- 会议记录中的明确决策或待决事项。

不按固定字数机械切割。必要时可进一步拆分过长章节，但应保留原始定位和上下文。跨章节引用应记录关联，不能因为信息分散而丢失。

## 3. 分析层次与信息提取

### 3.1 全局分析

识别：
- 产品目标和业务背景。
- 业务模块及模块边界。
- 核心业务流程。
- 用户角色及全局权限。
- 共享状态、规则和约束。
- 模块间依赖。
- 输入资料之间的关系、冲突和版本不确定性。

### 3.2 模块分析

针对每个业务模块，按资料实际内容动态提取：

- 业务场景与目标。
- 页面、弹窗、抽屉或其他前端载体。
- 用户角色和权限。
- 功能行为和用户操作。
- 展示规则、字段和数据格式。
- 业务规则与状态流转。
- 数据来源和数据依赖。
- 前后端协作关系及外部依赖。
- 异常场景和边界条件。
- 与其他模块、页面或共享规则的关系。
- 原始来源定位。

不是每个章节都必须包含上述所有类别。不得为填满模板而编造不存在的信息。

## 4. 前端相关性分类

不能简单地将信息分为“前端需求”和“非前端需求”。采用以下分类：

| 值 | 名称 | 定义 | 处理方式 |
|---|---|---|---|
| `direct` | 前端直接实现 | 前端需要直接实现的页面、展示、交互或客户端行为 | 进入需求清单和最终需求文档 |
| `collaborative` | 前后端协作 | 前端行为依赖后端接口、数据、状态或共同约定 | 保留前端职责、协作契约和依赖 |
| `contextual` | 必要业务上下文 | 本身不由前端实现，但影响前端展示、权限、操作或状态理解 | 保留为业务上下文或规则引用 |
| `irrelevant` | 与前端无关 | 不影响前端工作范围、行为、依赖或理解的信息 | 记录排除原因，不进入最终需求文档 |

例如，订单审核服务的内部实现可能属于 `irrelevant`；但订单审核状态定义可能属于 `contextual`，因为它会影响前端按钮、状态展示和操作可用性。

分类依据是对前端理解和实现的影响，不是资料内容的技术归属。

## 5. 信息确定性分类

| 值 | 名称 | 定义 | 表达要求 |
|---|---|---|---|
| `confirmed` | 已确认 | 原始资料明确说明，或存在可明确验证的权威依据 | 可作为正式需求陈述，并附来源 |
| `inferred` | 推断 | 原文未直接说明，但可根据多个已知条件推导 | 显式标记为推断，说明推断依据，不得伪装成已确认 |
| `uncertain` | 不确定 | 资料不足、语义歧义或缺少必要条件 | 标记待确认，不擅自补全 |
| `conflicted` | 冲突 | 不同资料对同一规则或行为给出不一致信息 | 保留各方依据、影响范围和待确认问题，不擅自裁决 |

确定性是信息属性，不是优先级。不能因为某个推断“看起来合理”就升级为 confirmed。

## 6. 需求范围识别

每项需求可记录本次需求范围状态：

| 值 | 名称 | 定义 |
|---|---|---|
| `new` | 新增 | 资料明确表明本次需要新增该能力或行为 |
| `modify` | 修改 | 资料明确表明本次需要调整已有能力或行为 |
| `retain` | 保留 | 资料明确要求本次保持现有行为不变，或明确声明该部分不调整 |
| `out-of-scope` | 不涉及 | 资料明确说明该能力不属于本次范围 |
| `unknown` | 未知 | 资料不足，无法判断当前是否存在或本次如何处理 |

必须遵守：

- PRD 未提及某功能，不等于该功能不存在。
- PRD 未描述现状，不等于功能已经存在。
- 不得仅凭常见产品习惯推断新增、修改、保留或不涉及。
- 无法判断时使用 `unknown`，必要时列入待确认事项。
- 本 Skill 不强制分析代码仓库，因此不能声称已验证当前线上或代码现状。

## 7. 统一需求信息模型

### 7.1 设计目标

每条可追踪的信息应有稳定 ID，支持多来源、多需求、多输出位置之间的关联。模型应能表达业务上下文、正式需求、推断、待确认事项及排除项。

### 7.2 推荐字段

| 字段 | 必需性 | 说明 |
|---|---|---|
| `id` | 必需 | 稳定需求信息 ID，例如 FE-ORDER-001 |
| `module` | 必需 | 业务模块标识；全局信息可使用 shared |
| `feature` | 建议 | 页面或功能标识 |
| `description` | 必需 | 信息内容或需求陈述 |
| `category` | 必需 | 信息类别 |
| `frontend_relevance` | 必需 | direct / collaborative / contextual / irrelevant |
| `certainty` | 必需 | confirmed / inferred / uncertain / conflicted |
| `sources` | 必需 | 一个或多个来源定位 |
| `dependencies` | 可选 | 依赖的需求信息、模块或外部能力 |
| `scope` | 必需 | new / modify / retain / out-of-scope / unknown |
| `notes` | 可选 | 推断依据、排除原因、补充说明 |
| `output_mapping` | 必需 | 进入最终文档的处理状态和目标位置 |

类别建议：
- `business-context`
- `page`
- `interaction`
- `display-rule`
- `business-rule`
- `permission`
- `data`
- `dependency`
- `exception`

按实际需要可以扩展类别，但不应让类别名称替代前端相关性或确定性字段。

### 7.3 来源定位

来源引用至少记录：
- `source_id`
- 文档名称或路径
- 章节、页面、图像或可验证的内容定位
- 必要时的摘录或简短依据说明

只有在资料确实提供页码、行号或其他精确位置时才记录精确定位。无法可靠定位时，记录可确认的章节或资料级位置，不得编造页码、段落编号或行号。

### 7.4 输出映射

每条需求信息都必须有明确处理结果：

| 状态 | 含义 |
|---|---|
| `included` | 已直接写入最终需求文档 |
| `merged` | 与其他信息合并表达，并保留关联 ID |
| `referenced` | 通过引用共享规则或其他统一位置呈现 |
| `excluded` | 不进入最终需求文档，必须记录原因 |
| `pending` | 尚未完成处理，必须暴露为质量异常或待确认事项 |

示意：

```yaml
id: FE-ORDER-001
module: order-management
feature: order-list
description: 订单列表需要展示订单状态
category: display-rule
frontend_relevance: direct
certainty: confirmed
sources:
  - source_id: SRC-001
    section: "2.2 订单状态"
  - source_id: SRC-001
    section: "3.1 订单列表"
dependencies: []
scope: modify
output_mapping:
  status: included
  target: requirements/order-management.md#order-list
notes: ""
```

以上是字段示意，不是强制要求每条需求都填写空数组或空字符串。具体模板在 Skill 实现阶段建立。

## 8. 信息整合与冲突处理

### 8.1 跨资料整合

同一业务规则可能分散在多个章节、原型和补充说明中。分析时应建立关联，将信息整合为完整需求，但保留所有来源关系。

关系包括但不限于：
- 同一需求的补充说明。
- 业务规则与页面行为之间的影响关系。
- 状态与操作可用性之间的关系。
- 角色权限与页面展示之间的关系。
- 页面功能与接口/外部系统之间的依赖。
- 不同资料对同一行为的冲突。

V1 使用结构化清单和关联索引即可，不要求建立知识图谱。

### 8.2 冲突处理

遇到冲突时：
1. 保留各来源的原始表述或准确摘要。
2. 标记冲突涉及的需求、模块和页面。
3. 说明冲突对前端行为或工作范围的影响。
4. 形成明确的待确认问题。
5. 在最终需求文档中标记冲突状态，不选择一方伪装为确定结论。

示例：主 PRD 写明审核失败后不可重新提交，补充说明允许重新提交，原型又出现重新提交按钮。不能自行选择任一来源作为最终规则。

## 9. 前端需求重构规范

最终需求文档应按业务模块组织，而不是按原始 PRD 章节组织。

模块文档可包含：

1. 模块概述：模块目标和边界。
2. 必要业务上下文：业务对象、状态、角色、关联模块。
3. 页面与功能：入口、布局、数据展示、筛选、操作、权限和异常场景。
4. 模块级规则：跨页面状态、权限、数据约束和共享行为。
5. 外部依赖：接口、其他系统和业务能力。
6. 待确认事项：影响理解或实现的缺失、歧义和冲突。
7. 需求来源：对应来源或需求 ID。

共享规则可以单独放在共享需求文档中，模块文档引用该规则，避免重复描述。

### 9.1 不得擅自增加产品交互

如果 PRD 只说明“提交订单审核”，不能自行将 Loading、重复点击禁止、成功后自动跳转、失败弹窗等补成正式产品需求，除非原始资料明确说明或这些行为有可验证的统一产品规范依据。

可以指出实现某个已确认行为时必需的技术处理，但必须区分：
- 产品明确要求的行为。
- 为实现已确认产品行为而必需的技术处理。
- 需要产品或设计决策的交互细节。

第三类应标记为待确认，不应作为已确认需求输出。

## 10. 长文档与多资料分析策略

- 先识别结构，再按章节、业务模块和资料单元分块分析。
- 不按固定 token 或字符数量机械切分。
- 每个分析单元记录处理状态和来源定位。
- 跨章节信息通过稳定 ID 和交叉引用关联。
- 完成局部分析后再进行全局整合，防止只按局部上下文做结论。
- 对无法读取的文件、图片或原型明确记录失败范围。
- 不能因部分内容无法读取而将整份资料标记为完整分析。

## 11. 推荐分析产物

V1 默认采用普通文件和结构化数据，不依赖数据库。

```text
analysis/
├── source-index.md
├── source-coverage.md
├── document-structure.md
├── business-context.md
├── requirement-inventory.yaml
├── cross-references.md
├── requirement-mapping.md
├── open-questions.md
└── quality-report.md
```

项目规模较小时允许合并文件，但必须保留对应信息和检查能力。

## 12. 输出语言与表达

- 默认使用用户指定的语言；未指定时沿用主要输入资料语言。
- 技术术语、接口字段和代码标识保留原始拼写。
- 面向前端开发人员，表达应具体、可定位、避免空泛口号。
- 不确定事项必须明确标记，不使用确定语气。
- 避免重复粘贴 PRD 大段原文；应重构表达并保留来源。
