# 质量保障规范

## 1. 文档目的

本文定义 `frontend-requirement-analysis` 的质量保障规范。核心是 **Requirement Traceability & Coverage（需求追溯与覆盖机制）**：确保原始资料中的前端相关信息得到分析和处理、需求清单中的信息得到合理呈现，以及最终前端需求文档中的正式需求均有可靠依据。

三层追溯闭环是 V1 的核心能力，不是可选的质量增强项。

## 2. 质量目标

质量检查必须回答三个问题：

1. **Source → Inventory：是否遗漏？** 原始资料中与前端有关的信息，是否都被识别并记录了处理结果？
2. **Inventory → Output：是否丢失？** 需求信息清单中应进入最终文档的信息，是否都得到明确呈现或合理处理？
3. **Output → Source：是否有依据？** 最终文档中的每项正式需求，是否都有原始资料依据，或被明确标记为推断、待确认或实现层面的必要说明？

此外还应检查状态一致性、关联有效性、资料可读性和文档内部一致性。

## 3. 三层追溯闭环

### 3.1 第一层：Source → Inventory

**目标：** 确保每个原始资料单元都被分析，且有可解释的处理去向。

#### 来源覆盖矩阵

对每份资料及其有意义的分析单元记录覆盖状态：

| 状态 | 含义 |
|---|---|
| `analyzed` | 已完整分析 |
| `partially_analyzed` | 仅部分分析，需说明未覆盖部分 |
| `failed` | 因读取、格式或其他限制无法分析 |
| `not_analyzed` | 尚未分析 |

“已分析但判断无需进入前端需求”与“没有分析”必须明确区分。

#### 分析单元处理结果

每个有意义的信息单元应有处理结果，例如：

- **retained**：提取为需求、业务上下文、依赖或规则。
- **excluded**：判断与前端无关，记录排除原因。
- **pending**：存在歧义、冲突或缺失，需要确认。
- **failed / partial**：无法读取或只完成部分分析，记录影响范围。

示例：

| 原始信息 | 处理结果 | 理由 |
|---|---|---|
| 订单状态定义 | retained | 影响前端状态展示和操作 |
| 订单审核权限 | retained | 影响操作入口和可用性 |
| 后端审核服务内部实现 | excluded | 不影响前端职责或理解 |
| 业务收入统计策略 | excluded | 与本次前端范围无关 |
| 审核失败后是否允许重提 | pending | 资料描述不一致 |

第一层检查必须能够回答“原始资料中的内容去了哪里”。

### 3.2 第二层：Inventory → Output

**目标：** 确保需求信息清单中所有应该保留的信息都正确进入最终前端需求文档，或有明确的排除理由。

每条需求信息必须有 `output_mapping`：

| 状态 | 含义 | 检查要求 |
|---|---|---|
| `included` | 已写入最终文档 | 目标位置有效 |
| `merged` | 与其他需求合并 | 记录参与合并的需求 ID 和目标位置 |
| `referenced` | 通过共享规则或其他位置引用 | 引用目标有效，读者可以找到内容 |
| `excluded` | 不进入最终文档 | 必须记录排除理由 |
| `pending` | 尚未处理 | 必须进入异常清单，不能静默遗留 |

例如，`FE-003` 的管理员订单审核权限可以通过 `referenced` 指向 `order-management.md#permission-rules`，而不是在多个页面重复写一遍。

检查重点：
- 是否存在没有输出映射的需求。
- 映射目标是否真实存在。
- 合并后是否丢失了原需求的关键条件。
- 引用是否能定位到共享规则。
- 被排除的信息是否有合理原因。
- pending 是否被明确暴露。

### 3.3 第三层：Output → Source

**目标：** 确保最终文档没有凭空增加正式产品需求，避免模型将常见产品习惯或主观判断写成原始需求。

最终需求文档中的每项正式需求必须满足以下之一：

1. 有一个或多个明确的原始资料来源。
2. 明确标记为 `inferred`，同时说明推断依据。
3. 明确标记为 `uncertain` 或 `conflicted`，作为待确认内容呈现。
4. 属于实现已确认产品行为所必需的技术说明，并与产品需求分开表达。

#### 不允许的行为

例如 PRD 只写“提交订单审核”，不能擅自增加以下正式产品行为：

- 提交时显示 Loading。
- 禁止用户重复点击。
- 成功后自动跳转到详情页。
- 失败后弹出特定样式的弹窗。
- 自动刷新列表或改变筛选条件。

除非资料明确规定，或有可验证且适用的统一产品规范作为依据，否则这些都是需要确认的产品交互决策，而不是可自动补齐的需求。

#### 多对多映射

追溯关系应支持：

- 一个来源产生多条需求。
- 一条需求关联多个来源。
- 一条需求在最终文档多个位置被引用。
- 多条需求合并成最终文档中的一段描述。

因此必须使用稳定的来源 ID、需求 ID 和输出定位，不得仅依靠相似文本或普通引用判断映射关系。

## 4. 其他质量检查维度

### 4.1 来源覆盖完整性

- 所有输入资料均登记在 Source Index。
- 每份资料均有可确认的结构或明确的结构识别限制。
- 每个有意义的分析单元均有覆盖状态。
- partial、failed、not_analyzed 均明确披露。
- 不把无法读取的资料视为已通过检查。

### 4.2 需求覆盖完整性

- 每条需求信息均有输出映射状态。
- 应保留的需求均已 included、merged 或 referenced。
- excluded 有理由。
- pending 已进入异常清单。
- 合并、引用没有丢失需求原有约束。

### 4.3 来源有效性

- 每项正式需求均可追溯到来源。
- 来源定位真实存在且足够准确。
- 推断、冲突和待确认内容具有明确状态标识。
- 不存在无来源且被写成 confirmed 的产品需求。
- 不将模型常识或经验当成用户资料中的明确要求。

### 4.4 状态一致性

检查需求清单与最终文档之间的以下状态是否一致：

- certainty：confirmed / inferred / uncertain / conflicted。
- frontend_relevance：direct / collaborative / contextual / irrelevant。
- scope：new / modify / retain / out-of-scope / unknown。
- output_mapping：included / merged / referenced / excluded / pending。

不得在最终文档中把清单中的 inferred 改写成 confirmed，也不得将 unknown 范围擅自写成 new 或 out-of-scope。

### 4.5 关联完整性

- source_id、requirement id 均稳定且唯一。
- 引用的来源和需求 ID 存在。
- 依赖关系指向有效对象。
- 文档路径和锚点有效。
- 合并与引用关系能够反向定位到原始需求。
- 不存在孤立映射或悬空引用。

### 4.6 文档可用性

- 最终文档按业务模块组织。
- 模块、页面、功能和共享规则边界清晰。
- 业务上下文足以支撑前端理解。
- 展示、操作、权限、状态、数据和依赖等信息按资料实际情况呈现。
- 术语和命名在不同模块中保持一致。
- 待确认事项不会被埋在普通描述中。

## 5. 质量检查执行方式

质量检查必须是明确的核对任务，而不是只让模型评价“文档是否完整”。

推荐执行顺序：

1. 遍历 Source Index，核对每个来源和分析单元是否有覆盖状态。
2. 遍历来源覆盖矩阵，核对 retained、excluded、pending、failed/partial 是否都有记录。
3. 遍历 Requirement Inventory，核对每条需求是否具有输出映射。
4. 遍历最终需求文档，逐项核对正式需求的来源或显式确定性标记。
5. 对照需求清单与最终文档，核对确定性、前端相关性和范围状态。
6. 验证所有来源 ID、需求 ID、文档路径、锚点和依赖关系。
7. 汇总异常并生成 Quality Report。

检查应尽可能逐项核对结构化清单与文档内容。不得只抽样检查后声称全量覆盖。

## 6. 异常管理

检查未通过时，生成异常记录。建议字段：

| 字段 | 含义 |
|---|---|
| `issue_id` | 稳定异常 ID |
| `check_layer` | source-to-inventory / inventory-to-output / output-to-source / consistency |
| `severity` | blocker / high / medium / low |
| `related_ids` | 相关来源或需求 ID |
| `description` | 异常说明 |
| `impact` | 对前端理解或交付的影响 |
| `recommended_action` | 建议处理方式 |
| `status` | open / resolved / accepted-limitation |

异常严重程度建议：

- **blocker**：关键输入无法识别，导致无法确定分析对象或核心需求。
- **high**：关键业务规则冲突、关键模块未分析或正式需求缺少依据。
- **medium**：部分需求映射缺失、重要上下文不完整或引用失效。
- **low**：非关键定位不够精确、文档表达或组织问题。

若异常可以在不改变业务含义的前提下修正，应先修正再复查。涉及产品决策或资料冲突时，不得为了消除异常而擅自选定结论。

## 7. 质量报告

`quality-report.md` 至少应包括：

1. 本次分析的输入资料范围。
2. 来源覆盖情况及未分析、部分分析、失败的资料单元。
3. 需求信息处理和输出映射的异常。
4. 最终需求文档中的来源依据检查结果。
5. 确定性、相关性和范围状态一致性检查。
6. 关联完整性检查。
7. 未解决异常及其影响。
8. 总体结论和分析限制。

可以报告明确核对的条目数量，但不得编造精确覆盖率或类似“98% 完整度”的主观指标。若计算比例，必须说明分母、计数口径和未覆盖项；无法可靠计算时不提供百分比。

## 8. 完成判定

一次分析可以在存在异常的情况下完成，但必须透明披露。

- **Completed**：三层检查均已执行，未发现未披露的高风险异常。
- **Completed with issues**：主要分析和检查已完成，但存在待确认、部分覆盖或其他未解决异常。
- **Incomplete**：关键资料无法读取、关键分析阶段未完成，或无法可靠执行必要的追溯检查。

不得为了得到 Completed 而隐藏、弱化或强行消除异常。对用户的完成报告应准确说明状态、主要产物、未解决问题和限制。

## 9. V1 质量边界

V1 不要求：
- 代码仓库自动验证页面或接口是否已经存在。
- 增量分析或历史版本之间的自动差异检查。
- 多 Agent 交叉审查。
- 数据库或知识图谱驱动的追溯平台。
- 以单一数字替代对异常内容的解释。

V1 必须具备：
- 来源覆盖矩阵。
- 结构化需求信息清单。
- 需求到最终文档的输出映射。
- 最终文档到来源的依据检查。
- 状态一致性与关联完整性检查。
- 可解释的异常清单和质量报告。
