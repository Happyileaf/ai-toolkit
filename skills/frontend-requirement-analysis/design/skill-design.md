# Skill Design Specification

## 1. 文档目的

本文定义 `frontend-requirement-analysis` Skill 的产品定位、目标用户、职责边界、输入输出、总体工作流程和交付结构。它是 Skill 的顶层设计依据；需求分析细则见 [Requirement Analysis Specification](./requirement-analysis.md)，质量与追溯规则见 [Quality Assurance Specification](./quality-assurance.md)。

本文描述的是目标设计，不意味着当前 Skill 已经实现全部能力。

## 2. 背景与问题

大型产品 PRD 往往同时包含业务背景、产品目标、业务规则、前后端职责、运营策略、数据分析、接口约束和多个业务模块。信息可能分散在主 PRD、补充说明、原型、流程图、接口文档和评审记录中。

前端开发人员，尤其是新加入项目或跨业务线支援的人员，通常需要先通读大量资料，再自行判断哪些内容与前端有关，并将分散的规则重新组织成页面、功能、状态和交互要求。这一过程成本高，也容易遗漏影响前端实现的上下文。

本 Skill 解决的不是“如何缩短 PRD”，而是“如何将完整产品资料转换成前端开发视角下可独立理解、可追溯的需求说明”。

## 3. 产品定位

### 3.1 核心定义

从前端开发人员的工作视角出发，对完整产品 PRD 及相关资料进行分析、筛选、理解、关联和重构，生成结构化分析资料，以及一份能够独立指导前端需求理解和开发工作的前端需求文档。

### 3.2 目标读者

- 未参与前期产品讨论的前端开发人员。
- 临时加入项目或跨业务线支援的前端开发人员。
- 需要快速理解前端工作范围、业务上下文和需求边界的研发人员。
- 负责需求交接、评审准备或需求完整性检查的产品与研发协作者。

### 3.3 预期结果

读者无需逐篇通读所有原始资料，也能通过最终文档理解：

- 为什么要做这项业务或功能，以及必要的业务背景。
- 本次前端涉及哪些业务模块、页面和功能。
- 页面需要展示什么、允许用户执行什么操作。
- 哪些角色、权限、状态和业务规则会影响前端行为。
- 前端依赖哪些接口、数据、外部系统或其他模块。
- 哪些行为是资料明确要求，哪些属于推断或尚待确认。
- 每项需求来自哪些原始资料，以及是否存在冲突或缺失。

## 4. 设计原则

1. **Frontend-oriented reconstruction**：围绕前端工作重新组织资料，而不是沿用 PRD 章节顺序。
2. **Context preservation**：保留前端正确理解和实现功能所必需的业务上下文。
3. **Evidence-based**：需求必须能追溯到原始资料；推断与待确认事项必须显式标识。
4. **No invented product decisions**：不擅自补充业务规则、交互行为、页面跳转或异常处理决策。
5. **Traceability by design**：从资料分析开始建立来源、需求和输出之间的关联。
6. **Transparent incompleteness**：资料不可读、覆盖不完整或存在冲突时，如实披露，不伪造完整性。
7. **Proportional structure**：根据项目规模调整文件拆分，不为追求文件数量而拆分。
8. **No premature infrastructure**：V1 使用文件和结构化清单即可，不引入数据库、向量数据库、知识图谱或多 Agent。

## 5. 职责边界

### 5.1 Skill 负责

- 理解全部输入资料及其相互关系。
- 分析文档结构、业务模块和核心流程。
- 识别与前端有关的信息及必要上下文。
- 整合跨章节、跨资料的规则和依赖。
- 重构前端工作范围、页面功能、展示、交互、状态、权限、数据依赖和异常场景。
- 标记信息确定性、范围状态、冲突、缺失和待确认事项。
- 建立需求来源映射与输出映射。
- 生成分析资料和最终前端需求文档。
- 执行三层追溯与覆盖检查，并报告异常。

### 5.2 Skill 不负责

- 重新设计产品需求、业务流程或产品策略。
- 擅自修改或裁决业务规则。
- 设计完整前端技术架构，或决定框架、组件、状态管理方案。
- 编写或修改业务代码。
- 自动拆分 Jira 等项目管理任务。
- 自动分析代码仓库作为 V1 的强制步骤。
- 把未确认的业务规则补写成正式需求。

Skill 可以识别技术实现约束和外部依赖，但不得越权做技术选型或技术方案决策。

## 6. 输入资料

不预设输入格式。一次分析可以包含：

- 主 PRD、补充 PRD、修订说明。
- Axure、Figma 等原型及页面截图。
- 业务流程图、状态图、架构图。
- API 或接口文档。
- 需求评审记录、会议纪要和补充说明。
- 用户明确指定的其他业务资料。

应建立资料清单，记录资料名称、类型、主要内容、涉及模块、版本信息（若可确认）和资料关系。资料关系可包括补充、修订、引用和冲突。不得仅凭文件修改时间推断哪个版本有效。

代码仓库不是 V1 的必需输入。若用户额外提供代码或明确要求结合代码分析，可以作为独立证据来源，但不能默认把代码现状当作产品需求。

## 7. 工作模式与总体流程

V1 采用一次性完整分析：收集本次分析范围内的资料，完成全量分析，直接生成交付物。不设置强制人工审核关卡；冲突、缺失、推断和高风险歧义写入交付物。只有关键输入缺失、无法确定分析对象或无法继续执行时，才向用户提出必要问题。

总体流程分为五个阶段：

1. **资料收集与理解**：识别输入资料、文档结构、业务模块及资料之间的关系。
2. **分块分析与信息提取**：按章节、业务模块或资料结构分析信息单元，记录前端相关信息及其处理结果。
3. **全局信息整合**：跨章节整合业务上下文、流程、状态、角色、规则、数据和依赖，识别冲突与缺失。
4. **前端视角重构**：识别前端工作范围，将分散信息组织为模块、页面、功能和共享规则。
5. **文档生成与质量检查**：生成分析资料和最终需求文档，执行三层追溯与覆盖检查，输出异常报告。

每个阶段的详细输入、处理规则和产物由 Requirement Analysis Specification 定义。

## 8. 关键设计决策

### 8.1 同时交付分析资料和最终需求文档

两类产物服务于不同目的：

- **分析资料**：记录输入资料、来源覆盖、需求信息清单、跨引用、映射、待确认事项和质量检查结果。
- **前端需求文档**：面向前端开发人员，呈现经过重构的业务上下文、工作范围和可理解的功能需求。

分析资料不是最终需求文档的替代品；最终需求文档也不能省略分析追溯所需的依据。

### 8.2 按业务模块组织最终文档

业务模块是一级组织结构。模块内部根据实际情况按页面、功能、流程或共享规则组织。跨页面和全局规则可以放在共享文档或模块级规则中，不强制将所有内容归入某一个页面。

### 8.3 全局分析与模块分析并行衔接

- 全局分析识别业务目标、模块边界、核心流程、全局角色权限、共享规则和资料关系。
- 模块分析细化页面功能、展示、交互、状态、依赖和异常。

全局分析不能替代章节和模块的详细分析，也不能成为跳过原始资料细节的理由。

## 9. 交付结构

建议的默认目录如下，具体文件按项目复杂度动态调整：

```text
frontend-requirements/
├── README.md
├── analysis/
│   ├── source-index.md
│   ├── source-coverage.md
│   ├── document-structure.md
│   ├── business-context.md
│   ├── requirement-inventory.yaml
│   ├── cross-references.md
│   ├── requirement-mapping.md
│   ├── open-questions.md
│   └── quality-report.md
└── requirements/
    ├── README.md
    ├── shared-requirements.md
    ├── <business-module>.md
    └── ...
```

说明：

- `analysis/` 保存可追溯的过程资料。
- `requirements/` 保存面向前端开发人员的最终需求文档。
- 小型项目允许合并文档；大型项目可按业务模块拆分。
- 不要求每个项目都生成所有文件，但任何省略都不能导致来源覆盖、需求去向或质量异常不可见。

## 10. V1 范围与后续扩展

### V1 包含

- 单次完整分析。
- 多种文档和资料格式的内容理解（以当前模型实际可读取能力为边界）。
- 全局与模块两级分析。
- 前端相关性分类和需求范围分类。
- 结构化需求信息清单。
- 三层需求追溯与覆盖闭环。
- 分析资料和前端需求文档双交付。
- 质量报告与异常清单。

### V1 不包含

- 增量分析、局部更新和跨轮次自动合并。
- 多 Agent 协作。
- 强制代码仓库分析。
- 自动生成完整前端技术方案。
- 自动拆分研发任务。
- 数据库、向量数据库、知识图谱等复杂基础设施。
- 强制人工审核工作流。

后续扩展应建立在稳定的需求信息模型和追溯关系之上，不改变 V1 的证据原则和职责边界。

## 11. 文档关系与维护

- 本文是 Skill 的顶层设计。
- [Requirement Analysis Specification](./requirement-analysis.md) 定义如何分析资料、建模需求和重构输出。
- [Quality Assurance Specification](./quality-assurance.md) 定义如何验证覆盖、依据和一致性。
- 若三份文档出现冲突，应先修订设计文档并保持相互一致，再更新 Skill 执行指令。
