# 前端需求文档结构

## 一、默认交付目录

默认使用 `frontend-requirements/`：

~~~text
frontend-requirements/
├── README.md
├── analysis/
│   ├── source-index.md
│   ├── source-coverage.md
│   ├── document-structure.md
│   ├── business-context.md
│   ├── requirement-inventory.yaml
│   ├── cross-references.md
│   ├── requirement-mapping.md
│   ├── open-questions.md
│   └── quality-report.md
└── requirements/
    ├── product-requirements-document.md
    └── references/
        ├── <supporting-document>.md
        └── ...
~~~

目录组织规则：

- `frontend-requirements/README.md` 保持为整个交付目录的总入口，职责不变。
- `requirements/product-requirements-document.md` 是唯一的主需求文档，也是需求内容的默认阅读入口。
- `requirements/` 下不创建 `README.md`。
- `requirements/` 下不默认创建共享需求文件，也不按业务模块分别创建文件。
- `requirements/references/` 仅用于存放确有必要从主文档拆分的补充内容；没有拆分需要时，可以不创建该目录。
- 不得为了匹配固定文件数量而创建无意义文件，也不能因为项目规模小就省略必要信息和追溯能力。

## 二、主需求文档

默认将需求内容集中写入 `product-requirements-document.md`。主文档应能独立呈现产品需求的整体结构和必要上下文，而不是仅作为其他文件的目录索引。

建议按照实际业务组织内容，通常可包含：

1. **文档说明**：分析范围、资料版本和阅读说明。
2. **产品与业务概述**：产品目标、核心业务对象、整体业务流程和模块关系。
3. **全局需求**：适用于整个产品或多个业务模块的规则。
4. **业务模块需求**：按业务模块设置章节，在章节内按页面、功能、流程或规则组织。
5. **跨模块关系与依赖**：模块之间的业务关联、状态/权限约束和依赖。
6. **异常与边界场景**：来源明确的异常行为及边界条件。
7. **待确认事项**：尚未解决的歧义、冲突和信息缺失。
8. **来源索引**：关联来源 ID、需求 ID 和必要的分析记录。

以上是组织建议，不是必须机械套用的固定模板。应根据实际需求调整章节，避免空章节或重复内容。

全局需求、共享需求和各业务模块需求默认都写在主文档中。共享规则应放在合适的全局章节，并在相关业务模块章节中说明其适用关系；不要为共享内容单独创建文件，也不要重复复制整段规则。

## 三、补充参考文档

拆分是例外，不是默认行为。只有以下情况确有必要时，才将详细内容拆分到 `requirements/references/`：

- 某部分内容规模很大，放在主文档中会明显影响整体阅读和维护。
- 某部分具有较高复杂度，适合独立展开，例如复杂业务流程、状态机或大量字段/规则细节。
- 某部分具有较强独立性，需要单独维护，或会被多个位置反复引用。

拆分时遵循以下规则：

1. 所有拆分出来的需求补充文档统一放在 `references/` 中。
2. 不得仅因为业务模块数量较多，就将模块逐一拆分成独立文件。
3. 主文档必须保留对应章节及必要的业务背景、核心需求和主要规则。
4. 主文档必须提供明确、有效的补充文档引用，说明引用内容及其用途。
5. 不得仅在主文档中留下链接而省略理解整体需求所需的基本内容。
6. `references/` 是主文档的补充，不是与主文档并列的需求文档集合。

## 四、顶层 README

`frontend-requirements/README.md` 的现有职责保持不变。它应作为整个交付目录的总入口，包含本次分析的目的和范围、简要业务背景与目标、前端工作范围概览、需求文档入口、分析资料和质量报告链接，以及影响开发的重要未解决问题。

其中需求文档入口应直接指向 `requirements/product-requirements-document.md`。如存在补充参考文档，可在主文档或顶层 README 中按需提供导航；不要为此在 `requirements/` 下新增 README。

## 五、写作规范

- 面向没有参加过产品讨论的前端开发人员。
- 来源有定义时，应具体说明执行角色、前置条件、可见状态、可用操作、操作结果和异常情况。
- 保留业务条件和原有术语。
- 在结构和语义上明确区分已确认需求、推断和待确认问题。
- 不要将技术实现建议混入产品需求陈述。
- 避免大段复制 PRD 原文，应重构信息并保留来源链接。
- 不得编造页码、接口名称、字段定义、UI 文案或文档锚点。
- 需求清单中的输出映射应指向主文档中的实际章节/锚点；拆分内容时，才指向 `references/` 中的对应文档，并确保主文档保留必要上下文。
