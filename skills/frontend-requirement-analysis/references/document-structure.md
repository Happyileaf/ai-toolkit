# 前端需求文档结构

## 一、核心原则

最终前端需求文档采用**单一主文档、按需拆分**的组织方式：

- frontend-requirements.md 是唯一主文档、唯一入口和默认阅读对象。
- 所有业务模块需求默认写在主文档中。业务模块是章节组织维度，不是文件拆分依据。
- 主文档应尽可能完整，读者只阅读主文档就应能理解整体业务、前端范围和主要需求。
- 只有主文档过长并明显影响阅读/维护，或某部分内容复杂、独立且确有单独维护价值时，才拆分子文档。
- 所有拆分的子文档统一放在 references/，并由主文档明确链接。主文档不能退化为目录索引。
- 不默认创建 analysis/、requirements/、README.md 或按业务模块拆分的文件。分析过程记录默认整合到主文档中。

## 二、默认交付目录

默认目录如下：

~~~text
frontend-requirements/
├── frontend-requirements.md
└── references/
    └── <topic>.md
~~~

说明：

- frontend-requirements.md 必须存在，是最终需求文档的唯一入口。
- references/ 默认不创建；仅在确有拆分必要时创建，不能为了预设目录结构而创建空目录或占位文件。
- references/ 只存放从主文档拆分出去的补充内容，例如复杂业务流程、庞大的字段/枚举字典、细粒度规则集，或过长的来源追溯明细。
- 不创建顶层 README.md 或 requirements/、analysis/ 目录。主文档本身承担文档说明、目录导航、需求承载和必要的追溯说明职责。

## 三、主文档内容组织

主文档应是一份可独立阅读的完整需求文档，而不是目录索引。可根据项目实际情况选择和调整章节，不要求机械生成所有章节。

建议结构：

~~~markdown
# Frontend Requirements

## 1. 文档说明
## 2. 项目概述
## 3. 前端需求范围
## 4. 全局业务说明
## 5. 业务模块需求

### 5.1 模块 A
### 5.2 模块 B
### 5.3 模块 C

## 6. 全局规则与跨模块行为
## 7. 页面与路由要求
## 8. 异常处理与边界场景
## 9. 非功能性要求
## 10. 待确认事项
## 11. 需求来源、追溯与质量检查
~~~

业务模块应直接作为主文档中的章节或小节。模块内部可按页面、功能、流程或业务对象组织；跨页面流程和模块级规则应放在合适的模块层级，不要强制将每条需求都归入某个页面。

共享规则默认放在主文档的全局章节中，模块章节引用对应章节或锚点，避免重复描述，也避免为共享规则单独创建文件。

## 四、分析记录如何融入交付物

来源索引、来源单元覆盖状态、需求信息清单、交叉引用、需求映射、待确认事项和质量检查结果是三层追溯所需的信息，但不意味着必须为每一类信息创建一个文件。

默认将必要信息直接组织在主文档中：

- 来源索引：列出来源 ID、资料名称/版本及必要说明。
- 来源覆盖：说明资料单元的分析状态和未覆盖原因；资料单元较多时可用紧凑表格汇总。
- 需求信息与映射：需求 ID 应出现在对应需求处，并能定位到主文档中的章节；合并、排除和待确认记录应保留必要关联。
- 质量检查：记录三层追溯的检查结论、限制和未解决问题。

当完整台账、映射表或其他过程记录过长，已经影响主文档阅读，或确有独立维护价值时，才将对应部分拆分到 references/。拆分后主文档保留摘要、结论和明确链接。不要将分析过程记录机械拆成多个小文件。

## 五、何时拆分到 references/

拆分是例外，不是默认动作。判断时应综合考虑：

1. 主文档长度是否已经明显影响浏览、定位和维护，而不只是超过某个字符数。
2. 某部分是否具有清晰、稳定、独立的主题边界。
3. 内容是否需要比主文档更细的独立维护，例如复杂业务流程、庞大的字段/枚举字典或细粒度规则集。
4. 拆分是否能改善阅读和维护，而不是仅仅把某个业务模块挪到另一个文件。

以下情况默认不拆分：

- 业务模块数量较多。
- 某个模块比其他模块内容稍多。
- 希望不同模块看起来各自独立。
- 仅为了缩短单个章节或让目录层级更整齐。
- 仅因为来源、需求或映射记录数量较多；应先评估是否能在主文档中使用紧凑表格或附录。

确需拆分时：

- 子文档统一放在 references/，使用能体现主题的文件名。
- 主文档保留该部分的目的、关键结论、核心规则、适用范围和明确的相对链接。
- 子文档开头说明所属主文档、适用范围和主题边界。
- 需求映射目标指向子文档中的实际章节锚点；主文档中保留对应入口。
- 不得产生没有主文档链接、无法确认归属或内容重复且不一致的子文档。
- 不得把所有模块拆成文件后，仅在主文档保留一份模块目录。

## 六、写作规范

- 面向没有参加过产品讨论的前端开发人员。
- 来源有定义时，应具体说明执行角色、前置条件、可见状态、可用操作、操作结果和异常情况。
- 保留业务条件和原有术语。
- 在结构和语义上明确区分已确认需求、推断和待确认问题。
- 不要将技术实现建议混入产品需求陈述。
- 避免大段复制 PRD 原文，应重构信息并保留来源链接。
- 不得编造页码、接口名称、字段定义、UI 文案或文档锚点。
- 优先通过主文档内部章节组织内容，不要将文件拆分当作模块化的默认手段。
